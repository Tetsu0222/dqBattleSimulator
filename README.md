# dqBattleSimulator

某RPGのバトルシミュレーター。初学者の頃にフルスクラッチで作成したものを、現在の自分がリファクタリングし、**「成長した点を言語化する」** ことを目的としたプロジェクト。

併せて、**JUnitを実戦の中で習得する** ことを学習目標として設定している。
本プロジェクトでのリファクタリング・ゴールデンマスター方式の採用は、この学習目標を達成するための手段として位置づけている。

---

## プロジェクト概要

ターン制コマンドバトル（味方パーティ vs モンスター）をWeb画面上で再現するシミュレーター。
通常攻撃 / 魔法 / 特技 / 防御 / 状態異常 / 蘇生 / 行動順制御 / 全体・グループ攻撃 など、本家RPGの主要メカニクスを実装している。

- **言語 / FW**: Java 17, Spring Boot 3.0.5
- **永続化**: Spring Data JPA + MySQL
- **ビュー**: Thymeleaf
- **ビルド**: Gradle
- **テスト**: JUnit 5 (Spring Boot Starter Test)

## スコープ

### やること
- **Javaコードのリファクタリング**: クラス / パッケージの責務分離、命名整理、手続き的コードのオブジェクト指向化
- **テスタビリティ向上**: 乱数のシード注入化など、テストから制御できる構造への変更
- **特性テスト（ゴールデンマスター）の整備**: リファクタ前後で振る舞いが同値であることを保証するテスト基盤を作る

### やらないこと（明示的にスコープ外）
- **DBスキーマの変更**: テーブル定義・カラム・リレーションは現状維持。エンティティクラス（`Monster`, `Ally`, `Skill`, `Magic`, `MonsterPattern`）の構造は触らない
- **新機能の追加**: 既存の戦闘ロジック以外の機能追加（新スキル、新ステータス等）はしない
- **UI / 画面デザインの刷新**: Thymeleafテンプレートの体裁変更はしない（必要最小限のみ）

スコープを絞る理由は、「成長した点の言語化」という目的に対し、変数を「Javaコードの設計力」に絞り込むため。

## 進め方の判断記録

未来の自分が軸を見失わないように、リファクタリングの進め方について下した判断と、その理由を記録しておく。

### 1. 真の学習目標は「JUnitの実戦的な習得」
これまで JUnit をきちんと使ったことがなく、本プロジェクトを実戦経験の場として位置づけている。
リファクタリング・ゴールデンマスター・特性テストといった手法はすべて、この学習目標に沿うように選んでいる手段である。
「テストを書く」こと自体が目的ではなく、「リファクタリングの安全網としてテストが必要 → だから書く」という必然性のある状況を作ることで、JUnit の使い方が自然に身につく構造を狙う。

### 2. ゴールデンマスター方式を選んだ理由
- **目的との整合**: リファクタリングの定義は「外部から見た振る舞いを変えずに内部を改善する」。ゴールデンマスターはまさに「外部から見た振る舞い」を凍結する手法であり、目的と手段が一致している。
- **古典的な単体テストとの違い**: メソッド単位の単体テストは内部構造に依存するため、構造を変えるとテスト自体を書き換えることになり、「テストが壊れたのか、コードが壊れたのか」を判別できなくなる。ゴールデンマスターは内部構造に依存しないため、この罠を避けられる。
- **規模との適合**: 入出力（HTTPリクエスト → ビュー名 + Modelの中身 + セッション状態 + ログ）が比較的明確で、シリアライズしやすい。この規模・性質はゴールデンマスター向き。
- **副次効果**: 各リファクタステップ後にテストを回すことで、バグの発生位置を時系列で局所化できる。結合試験単独では得られない情報。

### 3. リファクタリングの順序：「玄関（Controller）」から始める
- **効率面**: Controller は全ユースケースが集まる場所であり、ここを読み解く作業は自動的にアプリ全体の地図を描くことになる。Service層やドメイン層に手を入れる前の「無料の地図作成作業」として機能する。
- **影響範囲**: Controller の変更は影響範囲が比較的局所的（ビューとの接続だけ気をつければよい）で、最初のリファクタリング・サイクルを安全に回しきれる場所。
- **心理面**: 「玄関を綺麗にする」という区切りは完了が定義しやすく、燃え尽きを避けられる。綺麗になった部分が次の作業（Service層への着手）を呼ぶ勢いを生む。
- **想定される中間状態**: Controller が薄くなった分、汚さが Service層やドメイン層に転移して見える時期が来る。これは罠ではなく想定通りの中間状態であり、「玄関 → 居間 → 台所」という大きな順序を意識して進む。

### 4. 命名整理は優先度「低」で扱う
- **理由**: 変数名・定数名のリネームはコストの割に読みやすさへの貢献が小さく、構造の歪みを直すほうが優先度が高い。
- **例外**: typo・誤解を招く名前・公開APIの命名は優先度を上げる（誤読でバグを生む / 呼び出し側に波及する）。
- **運用**: ユースケース分割（Controller を複数に分ける / Service層を切る）のタイミングで、メソッドが新しいクラスに移る瞬間にリネームする。単独でリネームするより、構造変更と束ねて1コミットで済ませるほうが履歴が汚れない。

### 5. ゴールデンマスター更新の基準
- **リファクタリング中の赤**: 必ずコードを直す。ゴールデンの更新は禁忌。
- **機能追加・バグ修正中の赤**: ゴールデン更新が正解の場合あり。ただし変更内容を目視レビュー必須。
- この区別を曖昧にすると、ゴールデンが「現状追認装置」に成り下がり、安全網として機能しなくなる。

## テスト戦略 — 特性テスト（Characterization Test）

リファクタリング中の安全網として、**ゴールデンマスター方式の特性テスト** を導入する。

### 方針
1. **リファクタ前のコードを正とする**: 現状のコードが出力する戦闘ログ・最終状態を「期待値（ゴールデン）」として保存
2. **入力の決定論化**: `Random` をシード注入できる形に最小限改修し、同じ入力なら必ず同じ出力になる状態を作る
3. **代表シナリオを複数用意**: 攻撃 / 回復 / 状態異常 / 蘇生 / 全体攻撃 / 防御 / 混乱 / MP切れ など、分岐網羅を意識したケースを `src/test/resources/golden/` に配置
4. **リファクタの各ステップでテスト実行**: 全シナリオの出力がゴールデンと完全一致することを保証しながら段階的に構造を変えていく

### 「単体テスト」ではなく「特性テスト」と呼ぶ理由
クラス単位の振る舞い検証ではなく、`Battle` を中心とした **戦闘1試合まるごとの入出力同値性** を検証するため。
レガシーコードのリファクタリングにおける典型的なテスト戦略であり、Michael Feathers『レガシーコード改善ガイド』で示されている characterization test に該当する。

### 出力の正規化
ログにオブジェクトの `hashCode` やタイムスタンプが混入しないように、ゴールデン比較前に正規化を一段挟む。

## ディレクトリ構成（現状）

```
src/main/java/com/example/rpg2/
├── Rpg3Application.java           # エントリポイント
├── controller/                     # Spring MVC コントローラ
├── entity/                         # JPAエンティティ（DB対応）
├── repository/                     # Spring Data JPA リポジトリ
├── battle/                         # 戦闘の中核（Battle, AllyData, MonsterData, Target）
│   └── support/                    # Battle に紐づくサポートクラス群
├── action/                         # 行動（攻撃・魔法・特技）の実装
│   ├── magic/
│   ├── skill/
│   ├── startskill/
│   └── endskill/
├── process/                        # 戦闘中の手続き的処理（state-less な処理単位）
└── status/                         # 状態異常の実装（Poison, Sleep, ...）
```

## ライセンス / 注記

### 実装の出自について
本プロジェクトは、**某RPGのソースコードや内部資料を一切参照していない**。
プレイヤーとして観察した「振る舞い」（ダメージの傾向、状態異常の挙動、行動順の感覚など）から仕様を推測し、フルスクラッチで再実装したものである。

- 公式のソースコード・逆コンパイル成果物・リーク資料の類は使用していない
- 計算式・内部パラメータは実機の数値そのものではなく、観察に基づく自前の近似実装
- キャラクター名・固有名詞・グラフィック等の著作物は本リポジトリに含まれない（または学習目的で最小限に留める）

### 目的
学習・ポートフォリオ目的のサンプルプロジェクトであり、商用利用や原作の代替となることを意図していない。
原作およびその権利者へのリスペクトのもと、二次利用・配布は行わない。
