# 第1部: 事象記録（修正前）

## 一言サマリ
`PublicController` から `turnAction` / `isPossible` を `BattleProgressService` に切り出した際、`isPossible` 内で参照していたフィールド `turnqueue` の **初期化経路を移植し忘れた**。
特定条件下（死亡キャラの行動順が回ってきたとき）でのみ `NullPointerException` が発火する。
動作確認では正常系しか踏んでいなかったため、検出されないまま「完了」扱いになっていた。

## 事象
### 表面的な挙動
- リファクタリング後、画面上での通常の戦闘進行は問題なく動作していた
- ローカルでの動作確認では違和感が出なかった
- そのため、本トラブルは「リファクタリングの方針について整理する会話」の中で、コード読解により発見された潜在バグである

### 発見の経緯
1. リファクタリング後の `PublicController` を確認する流れで、依頼相手（AIアシスタント）が `BattleProgressService` の構造を確認
2. フィールド `private Queue<Integer> turnqueue;` がどこからも初期化されていないことを指摘される
3. `isPossible` 内で `turnqueue.peek()` を呼んでいる箇所があり、到達条件によっては NPE が発火することが判明

## 再現条件

### 発火する条件（推定）
`BattleProgressService.isPossible` が、以下のいずれかの分岐に入ったとき：
- 行動対象（actionObj）が **味方マップに存在し、かつ `survival == 0`**（戦闘不能）
- または、**敵マップに存在し、かつ `survival == 0`**

このとき [`BattleProgressService.java:38`](../../src/main/java/com/example/rpg2/battle/BattleProgressService.java#L38) または [`L66`](../../src/main/java/com/example/rpg2/battle/BattleProgressService.java#L66) の `turnqueue.peek()` が `null` 参照になる。

### 発火しない条件（=動作確認が通っていた理由）
- 行動対象が生存中（`survival != 0`）の場合、`turnqueue.peek()` には到達せず、`possible = true` を返して終了する
- つまり、戦闘中に **誰も倒れていない、または倒れたキャラの行動順が回ってこなかった** ケースでは発火しない

### 実機で踏みうるシナリオ
- 味方4 vs 敵4 で戦闘を開始
- 1ターン目で敵を1体倒す（または味方が1人倒される）
- 次ターン以降、倒したキャラ（または倒された味方）の行動順が回ってきた瞬間に NPE

## 影響範囲

### コードレベル
- 影響ファイル: [`BattleProgressService.java`](../../src/main/java/com/example/rpg2/battle/BattleProgressService.java) / [`PublicController.java`](../../src/main/java/com/example/rpg2/controller/PublicController.java)
- 影響メソッド: `BattleProgressService.isPossible`、`BattleProgressService.turnAction`
- 呼び出し元: `PublicController.next`（`/next` エンドポイント）

### 機能レベル
- 戦闘中の進行（`/next`）が、特定条件で例外終了する
- ユーザー体験としては「戦闘進行ボタンを押したら画面が壊れる」相当

### リファクタリングプロジェクトとしての影響
- リファクタリング Step1 の「完了」判定が、潜在バグを抱えたままだった
- 「画面で動作確認してOK」という完了判定基準そのものに不備があったことが露呈

## 原因分析

### 直接原因
`PublicController` から `BattleProgressService` に `isPossible` メソッドを移植する際、メソッド内で参照されていた **インスタンスフィールド `turnqueue` を Service クラスに同名で宣言したものの、初期化する経路を移植しなかった**。

その結果：
- リファクタリング前: `PublicController` のフィールド `turnqueue` は `start` メソッド内で `TurnQueue.getTurnQueue(turnList)` により初期化される
- リファクタリング後: `BattleProgressService` のフィールド `turnqueue` を初期化するコードはどこにも存在しない（`null` のまま）

### 根本原因（なぜそれが起きる土壌があったか）

**(1) コンパイラの限界**
- 同名フィールドが宣言されていれば、参照箇所はコンパイルエラーにならない
- 「未初期化フィールドへの参照」は静的解析で警告レベルでしか出ず、見逃しやすい

**(2) 動作確認の偏り**
- 動作確認が「正常系（全員生存中の戦闘進行）」に偏り、「死亡キャラの行動順スキップ」分岐に到達していなかった
- 「画面で動く」=「動いている」という思い込みが安全網として機能しなかった

**(3) リファクタリング切り出しの不完全さ**
- 「メソッドだけ移して、メソッドが依存していた状態（フィールド）の初期化経路の追跡が漏れる」というのは、メソッド抽出リファクタリングの古典的な落とし穴
- 切り出し対象メソッドが参照しているフィールドが、新クラスに移すべき状態なのか、引数として渡すべきデータなのかの判断が必要だったが、形だけ書き写してしまった

**(4) テストの不在**
- リファクタリング前に挙動を凍結するテスト（特性テスト）が無かったため、修正前後の振る舞い差分を機械的に検出できなかった

## 完了基準（修正前に先に決める）

以下の **3つの条件すべてを満たした時点で「完了」とみなす**：

### 基準1: 再現条件で NPE が発生しないこと
- 味方4 vs 敵4 の戦闘で、1ターン目に1体以上を倒した状態で次ターンに進む
- 倒したキャラの行動順が回ってきた瞬間に、`/next` が例外なく動作することを画面で確認
- 戦闘の通常進行（勝利または敗北まで）が完走することを確認

### 基準2: 正常系の挙動が修正前と同等であること
- 全員生存中の通常進行（攻撃・防御・魔法・特技）が、リファクタリング前と同じ挙動を示すことを画面で確認
- ターンカウント、ログメッセージ、画面遷移に変化がないこと

### 基準3: コードレベルで「同種の問題」が他に残っていないこと
- `BattleProgressService` のフィールド `turnqueue` が、未初期化のまま参照される構造になっていないことを確認（削除 or 引数化 or 初期化経路の追加のいずれか）
- 同じ移植ミスが他のフィールド（あれば）でも起きていないかを確認

### 完了基準として「あえて」含めなかったもの
- 自動テストの整備: 本来あるべきだが、Step1 のスコープでは「テスト戦略は別ステップで整備」と決めていたため、今回の完了基準には含めない。代わりに「再発防止」セクションで仕組み化を検討する

# 第2部: 対処記録（修正後）

## 修正内容

### 変更ファイル
- `src/main/java/com/example/rpg2/battle/BattleProgressService.java`
- `src/main/java/com/example/rpg2/controller/PublicController.java`

### 変更概要
1. **フィールド `turnqueue` の削除と引数化**
   - `BattleProgressService` のインスタンスフィールド `private Queue<Integer> turnqueue;` を削除
   - `turnAction` / `isPossible` の引数として `Queue<Integer> turnqueue` を追加
   - 再帰呼び出し箇所も引数を引き渡す形に修正
   - 呼び出し側 `PublicController.next` から `this.turnqueue` を引数として渡す
   - 結果として `BattleProgressService` がステートレスになった（将来の Spring Bean 化、DI 化の地ならしにもなった）

2. **`null` ガードの追加（暫定）**
   - `turnAction` 冒頭で `battle / actionObj / turnqueue` の `null` チェックを実施
   - いずれかが `null` の場合は WARN ログを出力し、`false`（ターン終了扱い）を返す
   - 暫定実装である旨をコメントで明示。本格的なエラーハンドリング設計は Controller のリファクタリング時に併せて行うことを記載

3. **`@Slf4j` の追加**
   - Lombok の `@Slf4j` で SLF4J ロガーを宣言（追加依存なし、Spring Boot 標準のロギングインフラに乗る）

## 完了基準に対する検証結果

### 基準1: 再現条件で NPE が発生しないこと → 達成
- **検証実施日**: 2026-05-10
- **検証手順**: 4対4 で戦闘を実施。勝利パターンと敗北パターンの両方を完走させた。両パターンとも戦闘中に味方/敵いずれかが倒れる経路を含むため、`isPossible` の「死亡キャラの行動順スキップ分岐」（=元のバグの発火箇所）に到達するシナリオを踏んでいる。
- **結果**: NPE は発生せず、両パターンとも正常に戦闘が完走した。

### 基準2: 正常系の挙動が修正前と同等であること → 達成
- **検証実施日**: 2026-05-10
- **検証手順**: 上記の戦闘進行において、ターン進行・ログメッセージ・画面遷移・勝敗判定の挙動を目視確認。
- **結果**: 修正前と同等の挙動を示すことを確認。コード変更の性質（引数追加 + 防御的ガード追加のみで、`isPossible` のロジック本体は変更なし）からも、挙動が変わる余地はない。

### 基準3: コードレベルで「同種の問題」が他に残っていないこと → 達成
- **検証実施日**: 2026-05-10
- **検証手順**: `BattleProgressService` のソースを再確認。フィールド `turnqueue` が削除されていること、メソッド引数として渡される構造になっていることを確認。
- **結果**: 「未初期化フィールドへの参照」という構造そのものが消滅。さらに暫定 `null` ガードに対する「サイレント問題化」のリスクも、コメントによる意図明示と WARN ログによる到達検知で解消。

## 振り返り

### 当初の仮説とのギャップ
直接原因の認識（=フィールド初期化経路を移し忘れた）は正しかった。

修正方針の選択について、当初は「同名フィールドを残して初期化経路を追加する」案も理屈上はあり得たが、**完了基準3「同種の問題が他に残っていないか」を先に明示していたことで**、構造的に正しい「引数化」を選ぶ方向に思考が誘導された。フィールドそのものを廃止することで、未初期化フィールドの問題を構造的に作り込めない形にできた。これは事前に完了基準を立てた効果として実感できた。

### 完了基準の妥当性
事前に決めた3つの基準は、このトラブルの完了判定として概ね妥当だった。

ただし基準3を厳密に解釈すると、暫定的な `null` ガードの `return false` は「サイレントに見逃される温床」になりうるという論点が修正中に浮上した。この論点は、**「適切なエラーハンドリングは Controller のリファクタリング時にスコープに入れる」** という別ステップへの持ち越し判断と、**「暫定であることをコメントで明示し、ログで到達検知できるようにする」** という現ステップでの対処の二段構えで解消した。

「完了基準の解釈」自体が修正中に深まる、という現象が起きたのは収穫だった。基準は固定の判定ラインではなく、修正過程で再解釈されうるものという認識を持てた。

### 今回の経験から得た一般化できる学び
- **メソッド抽出リファクタリングの落とし穴**: 抽出対象が参照しているフィールドは、「新クラスのフィールドにする / 引数にする / 別経路で渡す」のいずれかを意図して選ぶ必要がある。形だけ移すと初期化経路が断絶し、未初期化フィールドのまま残る。
- **動作確認の限界**: コンパイル成功 + 画面の動作確認では、分岐の片側にしか到達していない可能性がある。完了判定として「画面で動く」だけに依存するのは危険であり、自分の動作確認シナリオがコード上のどの分岐をカバーしているかを意識する必要がある。
- **暫定実装の正しい残し方**: 「暫定」を残す際は、**コメント（意図） + ログ（到達検知）** の二本立てが必要。コメントだけだと実行時に経路を踏んでも気づけず、ログだけだとコード読解時に意図が伝わらない。
- **完了基準を先に明示する効果**: 修正方針の選択肢が複数あるとき、完了基準が事前に明示されていると、より構造的に正しい選択肢に思考が誘導される。

### 仕組みでの再発防止（個人の注意力に頼らない策）
- **特性テストの導入**: 元々の計画に含まれている特性テスト（ゴールデンマスター方式）の必要性を、今回の事故が実例として裏付けた。次のリファクタリングステップでは特性テストを安全網として導入する。
- **暫定実装の標準フォーマット化**: 暫定的に `null` ガードや `return false` などを残す場合、「コメント + WARN ログ」の二本立てを習慣化する。
- **動作確認シナリオの拡充**: 「正常系（全員生存中）」だけでなく「異常系（誰かが倒れた状態）」もセットで踏むルールを意識する。

## 次のステップへの持ち越し
- **`BattleProgressService` の責務拡充**: 現状は `isPossible` のラッパーに近く、責務が空洞化している。Controller のリファクタリング時に、ターン進行の本体ロジック（[`PublicController.next`](../../src/main/java/com/example/rpg2/controller/PublicController.java) 内の戦闘終了判定・セッション操作）を Service 側に集約することを検討。
- **エラーハンドリング設計**: 今回暫定で導入した `null` ガード + WARN ログ + `return false` を、Controller リファクタリング時に正式な設計（例外スロー + Controller 層での集約ハンドリング等）に置き換える。
- **`BattleProgressService` の DI 化**: 現状 `new BattleProgressService()` で直接生成しているが、Spring Bean として `@Service` 付与 + コンストラクタインジェクションに切り替える。今回の修正でステートレスになったため、Bean 化しても並行アクセス問題は発生しない。
- **特性テストの導入計画**: 次のリファクタリングステップに着手する前に、特性テストの基盤整備を行う。
