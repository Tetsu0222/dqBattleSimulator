# 第1部: 事象記録（修正前）

## 一言サマリ
`PublicController` から `turnAction` / `isPossible` を `BattleProgressService` に切り出した際、`isPossible` 内で参照していたフィールド `turnqueue` の **初期化経路を移植し忘れた**。
特定条件下（死亡キャラの行動順が回ってきたとき）でのみ `NullPointerException` が発火する。
動作確認では正常系しか踏んでいなかったため、検出されないまま「完了」扱いになっていた。

## 事象
### 表面的な挙動
- リファクタリング後、画面上での通常の戦闘進行は問題なく動作していた
- ローカルでの動作確認では違和感が出なかった
- そのため、本トラブルは「リファクタリングの方針について整理する会話」の中で、コード読解により発見された潜在バグである

### 発見の経緯
1. リファクタリング後の `PublicController` を確認する流れで、依頼相手（AIアシスタント）が `BattleProgressService` の構造を確認
2. フィールド `private Queue<Integer> turnqueue;` がどこからも初期化されていないことを指摘される
3. `isPossible` 内で `turnqueue.peek()` を呼んでいる箇所があり、到達条件によっては NPE が発火することが判明

## 再現条件

### 発火する条件（推定）
`BattleProgressService.isPossible` が、以下のいずれかの分岐に入ったとき：
- 行動対象（actionObj）が **味方マップに存在し、かつ `survival == 0`**（戦闘不能）
- または、**敵マップに存在し、かつ `survival == 0`**

このとき [`BattleProgressService.java:38`](../../src/main/java/com/example/rpg2/battle/BattleProgressService.java#L38) または [`L66`](../../src/main/java/com/example/rpg2/battle/BattleProgressService.java#L66) の `turnqueue.peek()` が `null` 参照になる。

### 発火しない条件（=動作確認が通っていた理由）
- 行動対象が生存中（`survival != 0`）の場合、`turnqueue.peek()` には到達せず、`possible = true` を返して終了する
- つまり、戦闘中に **誰も倒れていない、または倒れたキャラの行動順が回ってこなかった** ケースでは発火しない

### 実機で踏みうるシナリオ
- 味方4 vs 敵4 で戦闘を開始
- 1ターン目で敵を1体倒す（または味方が1人倒される）
- 次ターン以降、倒したキャラ（または倒された味方）の行動順が回ってきた瞬間に NPE

## 影響範囲

### コードレベル
- 影響ファイル: [`BattleProgressService.java`](../../src/main/java/com/example/rpg2/battle/BattleProgressService.java) / [`PublicController.java`](../../src/main/java/com/example/rpg2/controller/PublicController.java)
- 影響メソッド: `BattleProgressService.isPossible`、`BattleProgressService.turnAction`
- 呼び出し元: `PublicController.next`（`/next` エンドポイント）

### 機能レベル
- 戦闘中の進行（`/next`）が、特定条件で例外終了する
- ユーザー体験としては「戦闘進行ボタンを押したら画面が壊れる」相当

### リファクタリングプロジェクトとしての影響
- リファクタリング Step1 の「完了」判定が、潜在バグを抱えたままだった
- 「画面で動作確認してOK」という完了判定基準そのものに不備があったことが露呈

## 原因分析

### 直接原因
`PublicController` から `BattleProgressService` に `isPossible` メソッドを移植する際、メソッド内で参照されていた **インスタンスフィールド `turnqueue` を Service クラスに同名で宣言したものの、初期化する経路を移植しなかった**。

その結果：
- リファクタリング前: `PublicController` のフィールド `turnqueue` は `start` メソッド内で `TurnQueue.getTurnQueue(turnList)` により初期化される
- リファクタリング後: `BattleProgressService` のフィールド `turnqueue` を初期化するコードはどこにも存在しない（`null` のまま）

### 根本原因（なぜそれが起きる土壌があったか）

**(1) コンパイラの限界**
- 同名フィールドが宣言されていれば、参照箇所はコンパイルエラーにならない
- 「未初期化フィールドへの参照」は静的解析で警告レベルでしか出ず、見逃しやすい

**(2) 動作確認の偏り**
- 動作確認が「正常系（全員生存中の戦闘進行）」に偏り、「死亡キャラの行動順スキップ」分岐に到達していなかった
- 「画面で動く」=「動いている」という思い込みが安全網として機能しなかった

**(3) リファクタリング切り出しの不完全さ**
- 「メソッドだけ移して、メソッドが依存していた状態（フィールド）の初期化経路の追跡が漏れる」というのは、メソッド抽出リファクタリングの古典的な落とし穴
- 切り出し対象メソッドが参照しているフィールドが、新クラスに移すべき状態なのか、引数として渡すべきデータなのかの判断が必要だったが、形だけ書き写してしまった

**(4) テストの不在**
- リファクタリング前に挙動を凍結するテスト（特性テスト）が無かったため、修正前後の振る舞い差分を機械的に検出できなかった

## 完了基準（修正前に先に決める）

以下の **3つの条件すべてを満たした時点で「完了」とみなす**：

### 基準1: 再現条件で NPE が発生しないこと
- 味方4 vs 敵4 の戦闘で、1ターン目に1体以上を倒した状態で次ターンに進む
- 倒したキャラの行動順が回ってきた瞬間に、`/next` が例外なく動作することを画面で確認
- 戦闘の通常進行（勝利または敗北まで）が完走することを確認

### 基準2: 正常系の挙動が修正前と同等であること
- 全員生存中の通常進行（攻撃・防御・魔法・特技）が、リファクタリング前と同じ挙動を示すことを画面で確認
- ターンカウント、ログメッセージ、画面遷移に変化がないこと

### 基準3: コードレベルで「同種の問題」が他に残っていないこと
- `BattleProgressService` のフィールド `turnqueue` が、未初期化のまま参照される構造になっていないことを確認（削除 or 引数化 or 初期化経路の追加のいずれか）
- 同じ移植ミスが他のフィールド（あれば）でも起きていないかを確認

### 完了基準として「あえて」含めなかったもの
- 自動テストの整備: 本来あるべきだが、Step1 のスコープでは「テスト戦略は別ステップで整備」と決めていたため、今回の完了基準には含めない。代わりに「再発防止」セクションで仕組み化を検討する

### 今回の経験から得た一般化できる学び

（候補：修正後の振り返り時に取捨選択して残す）
- リファクタリングで「メソッド抽出」を行う際は、抽出対象が参照しているフィールドを、新クラスのフィールドにするか / 引数にするか / 別経路で渡すか、を意図して選ぶ必要がある（形だけ移すと初期化経路が断絶する）
- 「コンパイル成功 + 画面の動作確認」では、分岐の片側にしか到達していない可能性がある。リファクタリングの完了判定として「画面で動く」だけに依存するのは危険
- 自分の動作確認シナリオが、コード上のどの分岐をカバーしているかを意識する必要がある（カバレッジ的な視点）

### 仕組みでの再発防止（個人の注意力に頼らない策）

（候補：修正後の振り返り時に取捨選択して残す）
- リファクタリング前に、対象メソッドが参照する全フィールドをリストアップする習慣（移植時のチェックリスト化）
- IDE / 静的解析の「未初期化フィールド警告」を warning から error に格上げする設定の検討
- 特性テスト（ゴールデンマスター方式）をリファクタリングの安全網として導入する（これは元々の計画に含まれている）
- 動作確認シナリオを「正常系 + 異常系（誰かが倒れた状態）」のセットで運用するルール化
